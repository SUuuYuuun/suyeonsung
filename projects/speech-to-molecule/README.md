# Speech-to-Molecule: 화학명 음성인식(ASR) 오류 연구 — 진행 기록

`서울대학교 학부생 연구인턴` · 김남준 교수 연구실 (AI with NVIDIA: Multimodal & Efficient Computing 트랙) · 팀 연구 · 2026-2 ~

> 음성으로 말한 IUPAC 화학명을 범용 ASR이 얼마나 깨뜨리는지 측정하고, LLM으로 올바른 화학명을 복원해 분자구조까지 재구성하는 연구.
> 이 문서는 **내가 맡은 부분(TTS 음성 데이터셋 구축 + 1차 ASR 오류 분석)**의 과정과 문제 해결 기록이다.

## 1. 연구 배경과 문제 정의

```
IUPAC Name → Spoken Text → TTS → ASR (Whisper large-v3) → LLM 오류 보정 → OPSIN / RDKit 검증 → SMILES · 분자구조
```

- 범용 ASR은 화학 전문용어에 약하다. 그런데 화학명은 **한 글자만 틀려도 다른 분자**가 된다 (`2-methyl` → `3-methyl`).
- 정확한 이름을 구조로 바꾸는 도구(OPSIN)는 이미 매우 정확하지만, **오류가 섞인 이름에는 취약**하다.
- 그래서 연구 질문을 *"음성 → 분자 시스템을 만든다"*가 아니라 *"ASR로 깨진 화학명을 화학적 검증을 이용해 LLM이 얼마나 복원할 수 있는가"*로 좁혔다.
- 팀 회의(2026-11-24)에서 정한 범위: 영어 · IUPAC 이름 기준 · 음성은 TTS로 생성 · ASR은 Whisper large-v3 · 범용 LLM 보정을 먼저 시험한 뒤 개선 방향 결정.

## 2. 내 역할

| 단계 | 한 일 |
|---|---|
| 데이터 검증 | 팀이 생성한 화학명 1,000개(pilot set)의 이름–구조 대응을 OPSIN으로 검증 |
| 발음용 텍스트 설계 | TTS가 숫자·기호를 잘못 읽지 않도록 변환 규칙 설계 |
| TTS 음성 생성 | 1,000개 음성 파일 + 정답 manifest 구축 |
| ASR 실행 | Whisper large-v3로 1,000개 받아쓰기 (Colab GPU) |
| 채점 · 분석 | 표기 / 문자 / 분자구조 3단계 지표 설계, 오류 유형 분류, 결과 보고서 작성 |

## 3. 진행 과정

### 3-1. 데이터 준비와 검증
- 팀원이 IUPAC 명명 규칙으로 생성한 화학명 5,000개 중 1차 실험용 상위 1,000개를 사용 (11개 클래스, dihaloalkane 54%).
- 이 데이터는 DB(PubChem)에서 가져온 것이 아니라 규칙으로 생성한 것이라, 실험 전에 **이름과 SMILES가 정말 같은 분자인지** 먼저 확인했다.
  - 방법: 정답 이름 → OPSIN → SMILES, RDKit으로 canonical 형태로 맞춘 뒤 데이터셋 SMILES와 비교
  - 결과: **1,000 / 1,000 일치** → 이후 결과에서 "정답 자체가 틀렸을 가능성"을 배제

### 3-2. 발음용 텍스트(Spoken Text) 규칙
- 문제: `3,5-difluoroundecane`을 그대로 TTS에 넣으면 `3,5`를 "삼천오백"이나 "35"처럼 읽을 수 있다. 그러면 나중에 생긴 오류가 **TTS 탓인지 ASR 탓인지 구분할 수 없다.**
- 해결: 숫자 사이 쉼표와 하이픈을 공백으로 바꾼 발음용 텍스트를 따로 만들었다 (`3 5 difluoroundecane`).
- 정답(`reference_text`)과 TTS 입력(`tts_input_text`)을 분리해 저장 → 오류 원인 추적이 가능한 구조

### 3-3. TTS 음성 생성
- 엔진: **edge-tts** (Microsoft 뉴럴 음성, 무료 · API 키 불필요), `en-US-AriaNeural`
- 출력: 16 kHz mono WAV (Whisper 입력 규격), 파일별 정답·클래스를 담은 manifest
- 진행: 100개 층화 샘플(클래스 비율 유지, 클래스별 최소 2개)로 먼저 파이프라인을 확인 → 1,000개로 확대
- 병렬 생성(동시 8개)으로 1,000개 생성 시간을 약 13분에서 3분 안팎으로 줄임
- 참고: 팀원은 Google Cloud TTS를 사용 → TTS 엔진에 따른 차이를 나중에 비교할 수 있음

### 3-4. ASR 실행 — 막혔던 문제와 해결

| 문제 | 원인 | 해결 |
|---|---|---|
| CPU로 돌리면 2시간 이상 예상 | large-v3(1.5B)는 CPU에서 느림 | Colab **T4 GPU** 런타임으로 전환 |
| faster-whisper가 오디오를 못 엶 (`metadata_errors` TypeError) | 오디오 라이브러리(`av`) 버전 불일치 | `soundfile`로 오디오를 직접 읽어 배열로 전달 |
| `libcublas.so.12` 로드 실패 | Colab의 CUDA 버전이 faster-whisper(CTranslate2) 요구 버전과 다름 | **같은 Whisper large-v3 모델**을 Hugging Face `transformers`로 실행 (beam 5) |
| CUDA Out of Memory | batch 16 × beam 5가 T4 16GB를 초과 | batch 8로 줄이고 최대 출력 길이 제한(`max_new_tokens=48`, 화학명은 짧음) |

→ 라이브러리 하나를 고집하지 않고, **모델(Whisper large-v3)은 그대로 둔 채 실행 방식만 바꿔** 실험 조건을 유지했다.

### 3-5. 채점 지표 설계
문자열이 같은지만 보면 화학적 의미를 놓치기 때문에 지표를 3단계로 나눴다.

| 지표 | 정의 | 왜 필요한가 |
|---|---|---|
| Exact | 대소문자 · 끝 마침표만 무시하고 동일 | 가장 엄격한 기준 |
| Compact / CER | 숫자 단어→숫자, 쉼표·하이픈·공백 제거 후 비교 | 표기 차이와 내용 오류를 구분 |
| **Structure match** | ASR 출력 → OPSIN → canonical SMILES == 정답 | **실제로 맞는 분자가 나오는가** (핵심 지표) |

오류 유형은 화학명 구성요소별로 나눴다: 위치번호(locant) · 할로젠(종류·개수) · 주사슬 길이 · 접미사(작용기)

### 3-6. 결과 검증 — 수치를 그대로 믿지 않기
- Colab에서 낸 1차 채점에서, 정확히 받아쓴 `1,2-dibromobutane`이 "구조 불일치"로 나오는 등 클래스별 수치가 이상했다.
- 원본 데이터셋의 SMILES를 기준으로 별도 환경에서 **다시 채점** → 전체 수치는 같았지만 클래스별 수치 일부가 바로잡혔다. 보고서에는 다시 채점한 수치를 사용했다.

## 4. 결과 (pilot 1,000)

| 지표 | 결과 |
|---|---|
| 완전 일치 | 9.6% |
| 표기 무시 일치 | 16.1% |
| 평균 CER | 15.4% |
| **분자구조 일치** | **12.1%** (121 / 1,000) |

**주요 오류 패턴**
- **주사슬 `-ane` → `-caine`** (370건): `heptadecane → heptadocaine`, `eicosane → icocaine` — 일반 영어 어휘(마취제 이름)로 끌려감. nonadecane은 0/123 정답
- **위치번호 구분 소실**: 위치번호 2개인 694개 중 쉼표 유지 242개, `3-5` 하이픈 293개, `2,11 → 211` 숫자 붙음 106개 (2,11과 21,1 구분 불가)
- **접미사**: `-yne` 18/19 오류(`5-Ein`, `But to wine`), `-ene` 19/19 오류(`Tridex 16`), `diol → Dial` 47건
- **할로젠**: 정확히 들은 비율 chloro 88% · bromo 78% · fluoro 68% · iodo 60%
- 클래스별: haloacid 42.1%(가장 높음, "…oic acid"는 일반 영어에 가까움) vs dihaloalkane 6.7%, diol 3.9%

**해석**
- ASR 출력을 그대로 쓰면 10개 중 1개 정도만 올바른 분자가 나온다 → 연구 동기(ASR 오류 보정의 필요성)를 수치로 뒷받침
- 오류가 무작위가 아니라 **패턴화**되어 있다 (`-caine`, 위치번호 붙음, 숫자의 단어화) → LLM 보정과 규칙 기반 보정이 모두 통할 여지가 있음
- 표기만 틀리고 내용이 맞은 경우가 65건 → 규칙 기반 정리만으로도 일부 복구 가능 (LLM이 필요한 부분과 구분 가능)

**한계**
- TTS 한 목소리라 실제 사람 발화와 다를 수 있음 · 데이터가 dihaloalkane에 편중 · 방향족·헤테로고리·입체화학 미포함

## 5. 다음 단계
1. 범용 LLM(GPT · Gemini · Claude) 보정 baseline: 같은 1,000개 출력을 보정 → 구조 일치율이 12.1%에서 얼마나 오르는지 비교
2. 보정 후에도 남는 오류 유형 분석 → OPSIN/RDKit 검증 결과를 다시 LLM에 돌려주는 **Agentic 보정 루프** 설계
3. 다른 TTS 음성 / 사람 녹음 소규모 세트로 결과 일반화 확인

## 6. 배운 점 (자소서 메모)
- **문제를 측정 가능한 형태로 바꾸기** — "ASR이 화학명을 잘 못 듣는다"는 막연한 문제를 3단계 지표와 4가지 오류 유형으로 나눠 수치화했다.
- **오류 원인을 분리하는 실험 설계** — 정답과 TTS 입력을 분리하고 데이터셋을 미리 검증해, 결과의 오류가 ASR에서 온 것임을 보장했다.
- **제약 속 문제 해결** — 라이브러리 버전 · CUDA · 메모리 문제를 하나씩 원인부터 짚어 해결하되, 실험 조건(모델)은 바꾸지 않았다.
- **결과를 의심하고 검증하기** — 이상한 수치를 그냥 넘기지 않고 다른 환경에서 재채점해 바로잡았다.
- 신소재공학 전공의 IUPAC 명명법 지식이 오류 유형 설계(위치번호 · 할로젠 · 주사슬 · 접미사)에 직접 쓰였다.
